# 2026-08-05 工作日志

## 修复微信支付 FREQUENCY_LIMITED 和短信验证码闭包陷阱

### 问题1: 微信支付 [FREQUENCY_LIMITED]
- **根因**: 前端 `WechatEnterpriseCheckout` 的 `useEffect` 在 React StrictMode 双调用或组件重渲染时重复调用 `create-order` API，导致微信侧频率限制。后端每次请求都重新调微信 API 创建订单，没有缓存 `code_url`。
- **修复**:
  - 前端: 用 `createdRef` + `creatingRef` 两个 ref 防止重复调用，重试按钮改为 `setRetryKey` 重触发 effect 而非刷新页面
  - 后端: `create-order` 路由添加 `code_url` 内存缓存（Map<outTradeNo, {codeUrl, expiresAt}>，TTL 2小时），同一订单不重复调微信 API。若收到 FREQUENCY_LIMITED 错误，尝试返回缓存
- **文件**: `components/pay/wechat-enterprise-checkout.tsx`, `app/api/payments/wechat/create-order/route.ts`

### 问题2: 短信验证码 MathCaptcha 闭包陷阱
- **根因**: `MathCaptcha.doVerify()` 从 React state 读取 `answer`，但在 `setTimeout` 防抖回调中，闭包捕获的是旧值（空字符串），导致 `parseInt("", 10) = NaN` → 提示"请输入数字答案"。防抖验证失败后，用户只能靠回车触发（且回车处理仅在防抖尚未触发时生效）。
- **修复**:
  - `doVerify` 改为接收参数 `currentValue: string`，不再从 state 读取
  - `handleChange` 将最新输入值 `val` 直接传入 `setTimeout(() => doVerify(val), 300)` 回调
  - 防抖从 600ms 降至 300ms
  - `handleKeyDown` 的 Enter 处理也改为传 `answer` 参数，且不再依赖 `debounceRef.current` 是否存在
- **文件**: `components/auth/math-captcha.tsx`

### 问题3: 支付金额不一致（展示1分钱但实际支付62元）
- **根因**: `create-checkout.ts` 去重逻辑只检查 packId/target 是否相同，不检查金额。调价后旧的 62 元待支付订单仍被复用返回，导致前端拿到旧金额。
- **修复**: 去重条件增加 `Number(existingPending.amountYuan) === amountYuan` 金额校验。同商品但金额不同时，将旧订单设为 CANCELLED 并创建新订单。
- **文件**: `lib/payments/create-checkout.ts`
